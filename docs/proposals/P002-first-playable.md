# P002｜P1 首个完整对局的最小玩法边界

- **主题**：游戏设计
- **来源**：原拟发布的 Discussion D02
- **阶段**：P1
- **状态**：待评估；尚未拆成开发 Issue
- **归属**：[候选池](../EVOLUTION_POOL.md)

## 目标和失败场景

首个版本的底线：普通玩家从“新建游戏”开始，在不打开开发者工具、不人工修改内部状态的条件下，能够一直玩到合法的胜负结算。

失败场景包括：只能展示静态棋盘；骰子移动无实际规则；现金或产权计算错误；对局无法结束；关键操作只有开发人员会用；游戏需要英文界面。

## 初步候选范围

- 一张简化但闭合的棋盘；定义土地格与起点，设定可复现随机种子。
- 玩家初始资金、回合顺序、掷骰、按格移动、到达后的规则处理。
- 地产购买、所有权、对手踩地付租、资产与破产判定。
- 起码可由一名玩家在一台电脑上完成游戏：可以先选基础电脑对手，也可评估本地轮流控制的替代路线。
- 简体中文按钮、反馈、资产信息、规则说明和胜负提示。
- 规则逻辑与 React 展示分离，允许无需浏览器地快速模拟对局。

**不预先要求**完整股票市场、全部角色、海量卡片、多张地图或原版画面；避免为了“像原版”迟迟做不出完整对局。

## 需要研究的问题与候选方案

1. **人数**：首版采用 1 名人类 + 1–3 名基础电脑，还是本地多人轮流？对单人可玩性、测试复杂度分别有什么影响？
2. **地图**：多少格足以验证买地、租金与胜负，并让一次自动模拟速度合理？
3. **经济规则**：初始现金、地价、租金、破产条件如何保持可解释，后续参数怎样可调整？
4. **验收**：怎样同时保留固定种子自动模拟、规则单元测试和浏览器中完整真实对局的证据？

## 准备晋升 Issue 的条件

候选功能必须有玩家可观察的结果、合法操作边界、明确胜负判据、能复现的测试用例、依赖与回退方式。先挑能闭合 P1 的少量切片，不把整份提案直接当作执行任务。

**参考验收**：能稳定完成至少一次真实完整对局；规则测试覆盖资金、产权、租金、破产等关键转移；没有必须靠修改内存才能走下去的步骤。具体实施基准仍须在执行任务中量化。
