# P004｜AI 自主改进如何晋升为 Issue

- **主题**：定向进化治理
- **来源**：原拟发布的 Discussion D04
- **阶段**：P0–P5 持续适用
- **状态**：治理原则已获批准；2026-10-15 完成首次提案筛选及晋升；后续编码、独立验收与自主持续循环待验证
- **归属**：[候选池](../EVOLUTION_POOL.md) · [协议](../AUTONOMOUS_EVOLUTION.md)

## 核心假设

AI 必须可以自主发现改进，但不应该把未经筛选的所有想法都塞进 Issue；Issue 只留给具体、可执行、可验收的工作。

统一采用**仓库内 Markdown 提案池**，因为当前负责维护仓库的 AI 可以直接通过 GitHub 连接编辑仓库文件，却不能可靠创建或更新 GitHub Discussions。

## 目标层与成熟度层

目标层：永久双目标 → 阶段目标 → 能力领域 → 可交付功能 → 原子任务。前三级主要是文档，不强制建 Issue。

成熟度层：**观察/假设 → 提案池登记 → 研究去重/比较 → 评审 → 晋升 Issue 或延期/否决 → PR → 独立验收 → 结果回写**。

两层彼此独立：一个跨阶段提案可以长期保留；一个当前阶段的缺陷也可以迅速晋升。

## 候选准入门槛

- 与当前阶段目标或明确已知缺陷有直接关系。
- 有证据或者具体可验证的能力缺口，且与现存提案、Issue 不重复。
- 玩家价值或工程价值可说明；修改范围与风险可控制。
- 有验收标准、必要依赖、回滚方案与成本判断。
- 已批准待执行队列初期建议保持在 10–20 项以内；同时开发 3–5 项以内。超过容量则保留在候选池。
- **确认的严重 Bug 可直接建 Issue**，但必须在来源记录中注明“紧急直入”。

评审结论只能为：晋升、继续研究、延期、否决。不得通过“提案多”“代码多”“提交多”认定进化成功。

## 必须认真验证的问题

1. 谁负责去重与控制候选规模？是否会产生一堆永远无人复核的提案？
2. 如何分离实施者与验收者，防止修改测试来骗取通过？
3. AI 如何将失败实验的结论回写，而不是重复尝试同一无效方向？
4. 哪些连续失败、回归或资源损耗会触发停止与升级人工处理？
5. 怎样衡量真实功能增益、回归率、首次通过率、人工介入与实际成本？
