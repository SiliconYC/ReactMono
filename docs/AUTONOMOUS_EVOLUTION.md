# AI 自主定向进化协议

## 实验问题

能否在仅提供长期目标、系统约束与独立验收标准的情况下，让 AI 持续发现有价值的改进，自己建 Issue、完成代码与测试、提交和合并，使游戏经过多轮后真实变好？

核心是**候选改进 → 可执行变更 → 独立验证 → 接受/拒绝 → 下一轮**，而非仅让 AI 连续生成代码。

## 职责分离（是逻辑角色，不强制每项都启用独立模型）

- **规划者**：审查产品缺口、缺陷、测试报告、玩家体验，去重并提议任务优先级。
- **实施者**：围绕已定义的验收标准，尽量小步、原子化地修改并提交。
- **验收者**：独立运行测试，检查可玩结果和负面影响，有权退回、回滚或阻断合并。
- **协调者**：控制任务依赖、并发上限、失败重试、进度账本和迭代预算。

同一 Agent 可以承担多个职责，但**不能只依赖实施者自己声称成功**。关键验证应由独立自动测试或其他审查过程执行。

## 候选 Issue 从何而来

- 与产品目标或已确定里程碑之间的功能缺口。
- 规则单元测试、批量模拟、浏览器测试或真实玩家反馈暴露的问题。
- 界面操作困难、动画不顺、加载问题、对局失衡、可用性改进。
- 重复且客观可证实的开发阻塞（例如测试不可复现、构建不稳定）。

每项提议应有可核验的来源、玩家价值、最小改动范围和明确验收办法。重复 Issue 应合并、链接或关闭，不追求数量。

## Issue 最低字段

1. **问题与证据**：哪种场景失败、如何复现，或明确缺失何种玩家能力。
2. **完成目标**：完成后玩家能够做什么，或哪些可观测行为应该改变。
3. **验收标准**：可判断的测试、行为、界面证据及失败条件。
4. **边界与依赖**：涉及模块、依赖的其他 Issue、兼容性及风险。
5. **验证与回滚**：验证命令、随机种子/测试存档、预期不受影响的功能、失败后如何回退。

## 一轮执行协议

1. 对齐最新 `dev`、可玩状态、测试和已有 Issue。
2. 选择价值高且可独立验收的一小批 Issue；依赖冲突的任务不并行。
3. 为任务建立从 `dev` 派生的工作分支；小型授权文档操作可直接进 `dev`。
4. 实施、编写/补齐相关测试、保存可复现证据并提交。
5. 由独立验收者检查：原有测试、目标验收、游戏能否照常运行、关键性能及必要的画面检查。
6. 通过则 PR 合并回 `dev`、关闭 Issue，记录实际结果；未通过则修复/回退/注明阻塞。**禁止默默修改目标以自称成功。**
7. 根据新增证据决定下一轮的任务；若连续失败或效益下降，应调整策略而非无限重试。

## 必须保存的进化账本

建议后续采用 Issue、PR、提交与自动测试报告组成可追溯记录。每轮至少关联：

- 来源 Issue 与变更 PR/提交。
- 变更前后可验证的差异；重点记录新增的真实玩家能力。
- 测试结果及保留的失败记录。
- 是否出现回归、是否需要人工介入、是否回滚。
- 可取得时的耗时、Token 或运行成本；数据缺失应标注，不能补造。

## 不可自我修改的红线

- 不得未经所有者明确授权改变“做出完整游戏”与“`dev` 是目标分支”这两个目标。
- 不得通过删除/弱化回归测试、伪造验收记录、无依据关闭 Issue 来提高成绩。
- 游戏未能完整可玩时，不要仅为增加功能数量而大面积扩张范围。
- 不得无上限增殖 Issue、创建无限循环或大量积累无人验收的 PR。
- 不得擅自启用收费服务、泄露密钥或修改 `main`。

## 关于真正的无人值守

本文件是代理行为规范，**不是正在运行的调度系统**。要开展连续自主进化，仍需后续建立实际的触发器、工作执行环境、GitHub 写入权限管理、并发限制、日志与失败恢复机制。初始化阶段不宣称已经实现无人值守。

建议先通过一小批真实任务验证“提 Issue → 实现 → 独立验收 → 合并 `dev`”完整循环，再扩大并发和自主权。
