# 大富翁仓库：六阶段路线图

> 状态：2026-10-15 首轮阶段基线，具体边界仍可在仓库提案中研究修订。阶段是能力门槛，不是固定工期；未达到验收不得宣称完成。
> **双目标**：①做成真正能玩、能玩完、好玩的游戏；②验证 AI 自主发现问题、讨论、选择、实施、验收和持续改进。
> **硬约束**：仅静态 GitHub Pages / PWA，不依赖运行时服务器；不做游戏账户、登录、云同步；本地存档与手动备份；游戏界面仅简体中文；所有默认开发和合并目标均为 `dev`，不触碰 `main`。

## 路线图总览

| 阶段 | 产品主线：交付给玩家的能力 | 定向进化实验主线 | 退出验收 |
| --- | --- | --- | --- |
| **P0 · 定义目标与治理**（治理文件已建立） | 确定游戏边界、阶段、可验收的规则基线；暂无游戏代码 | 建立 Markdown 提案池→候选评审→少量 Issue→PR→独立验收的规约，并保留首批五份提案 | 目标一致、职责明确、候选想法不会直接涌入 Issue；不把文档冒充游戏 |
| **P1 · 第一局能玩到底** | 一张小地图，至少人类对电脑/本地轮流两种方式中的一种可独立开局；掷骰、走格、买地、收租、回合、破产、胜负；全程简体中文 | 首次实证“从目标生成候选→精选 Issue→实现→测试→合并 dev”；保留失败证据 | 普通玩家无需调试工具能完整结束一局；确定性规则单测＋自动模拟＋浏览器实玩验证 |
| **P2 · 可靠的准本地游戏** | 土地升级、基础卡片/道具、随机事件、可用电脑玩家；GitHub Pages 发布；PWA 离线启动；本地多存档位、读档、自动保存、导入导出 | 测量自主任务的实际交付率、回归率、人工干预次数，建立缺陷反馈闭环 | 断网后能继续玩；关闭后读档可续局；导出再导入可恢复；若存储清除有明确警示；通过跨版本存档测试 |
| **P3 · 丰富核心玩法** | 扩展角色、多地图、地产/建筑、银行与股票、完整度逐渐提高的卡片和道具、特殊状态、策略型电脑玩家 | AI 主动从模拟对局、测试、交互中提出玩法和技术改进，并比较候选方案 | 主要系统在真实对局中可用且互相兼容；经济/产权守恒、合法操作、存档一致性有大量自动模拟证据 |
| **P4 · 高完成度正式版** | 界面、美术、音效、动画节奏、人物辨识度、性能与易用性；内容丰富但尊重玩家节奏 | 为自动化评价设置上限：视觉与趣味性需要独立审查和真人判断；测量失败/回滚 | 一局可重复稳定完成；关键操作与信息清楚；功能、存档、断网、性能、视觉回归整体达标 |
| **P5 · 长期自主进化** | 围绕真实缺陷、平衡性和体验小步迭代，持续发布可靠改进 | 目标实验：连续 **30 轮**有来源、有变更、有独立验收的自主改进；能拒绝差方案、回滚及保存教训 | 展示改进前后证据和净收益；没有通过弱化测试或堆砌 Issue 换取“成果” |

**关键说明**：P5 是“自主进化成熟度”的里程碑，不代表直到 P5 才开始自主试验。进化主线从 P0 开始，每一阶段都要产生真实证据；各阶段的某些技术任务可以前置，但不得牺牲当前可玩闭环。

## 游戏范围的取舍

- **优先级一：真正可玩**。先跑通完整对局，再扩张股市、人物、地图、道具、美术。
- **优先级二：准本地体验**。网站可安装、断网继续游戏、本机离线存档；多电脑间的手动文件拷贝不属于自动同步。
- **简体中文是硬约束**。游戏界面、提示、错误消息、按钮、规则解释、教程、存档 UI 均使用简体中文；早期不引入英文版和多语言工程。
- **参考原作的乐趣与机制，不默认复制受保护的资源**。原版素材只有明确获得授权才引入；否则做原创替代。
- 具体游戏功能的阶段归属可通过提案池中的评审调整，但必须说明对当前阶段退出验收的影响。

## 阶段验收方法

每阶段均需保留：
1. 玩家可观察的真实能力清单和清楚的失败条件。
2. 无界面规则测试、固定随机种子模拟、浏览器端到端验证；图形阶段还需视觉审查。
3. 上阶段核心功能回归、存档兼容性与重要已知缺陷。
4. 每项自主实施关联仓库提案 / Issue / PR / 变更前后证据；失败也登记。
5. 独立于实施者的验收；不能靠修改测试标准宣布完成。

## 目标层与流程层分开

- **目标层**：永久双目标 → 当前阶段 → 能力领域 → 已批准可交付功能 → 原子实施任务。
- **流程层**：观察与假设 → Markdown 候选提案（去重、比较、收集证据）→ 晋升审查 → Issue（仅可执行项）→ PR → 独立验收 → 回写结果。
- 不强迫所有目标层级都变成 Issue。跨阶段能力（例如存档、电脑玩家）由路线图与领域文档跟踪。
- 已证实的高优先级 Bug 可以直接成为 Issue，无需先开会。
- 初期同时开发最多 **3–5** 个 Issue；待执行批准队列建议 **10–20** 个，超过容量则保留在候选池。
- 提案可以被保留、延期或否决；不要求所有想法最终都进入 Issue。
