# 主程序游戏界面与交互重设计方案

日期：2026-10-18。审查基线：本地 `dev@87dcb61`。性质：设计与实施建议，尚未实施、未建立新 Issue、未修改仓库。

## 1. 目标与边界

让玩家进入后能够认出这是游戏；对局中能够迅速理解谁在行动、正在发生什么、下一步能做什么；复杂金融和资产操作完整保留，但按场景出现。延续 4173 demo 的清晰层级、玩家卡、底部行动条、独立金融窗口和顺畅因果，而不是把 demo 的全部空间安排机械放大。

保持静态 GitHub Pages/PWA、本机存档、简体中文、无账号/云同步/后端，开发与集成目标仍为 dev。第一轮不重写经济核心、不升级 React/Three/R3F、不引入通用游戏引擎，不改变现金/存款分账、到访建设一次、AI、胜负和存档语义。

本次只规划。下面所有组件名、时长、布局预算和测试数量均是拟议目标，不代表已实现或已验收。布局示意中的地块名称与数字是样例。

## 2. 核实的现状

已阅读 README、项目宪章、路线图、候选池、自主演化协议及既有 P006/表现架构；实际访问 4174 与 4173，在单独检查页完成主程序默认种子开局、掷骰、购买、展开银行。

### 2.1 买地重播骰子：表现缺陷已确认

- 主程序 `src/ui/app.tsx:597` 从完整历史找最近骰点，`:658` 把每次变化的 `game.revision` 传为 `dieNonce`。
- `src/demo3d/world/Dice.tsx:47` 的 effect 在 nonce 变化时重设动画起点。购买、升级、存取等成功命令都会增加 revision，因此会重播旧骰点；换到新玩家时还可能挂载携带旧值的骰子。
- 实际默认流程：种子 20261015，掷出 1 点，到地产 1，买入 110。页面变为现金 1390、位置仍为 1。
- 对已有编译规则模块作定向核查：购买前后 revision 2→3，新增事件只有 property_bought，骰子事件累计数 1→1，位置 1→1，randomState 不变。
- 结论：本次确认的是旧投骰动画被重新触发，不应把它误写成规则层再次抽随机数。仍需浏览器回归覆盖其他买地种子及连续操作。

### 2.2 镜头突变：代码原因已确认

- 主程序 `src/ui/app.tsx:659` 用 activeMotion 是否存在决定 followCurrent；移动开始进入跟随，移动清除立刻回全景。
- `WorldCanvas.tsx` 的 CameraRig 平滑了 look 目标，但 camera.zoom 每帧直接赋两种值，未作缩放插值。
- 当前跟随只关注视口尺寸，不了解 HUD 占位和可见棋盘安全区域。
- 因此需要拆开“玩家选择的镜头模式”和“当前演出是否有路径”，让缩放、目标、构图一起过渡。

### 2.3 移动有两套不一致的时钟

- 主程序 cueFor 使用每格 85ms 加尾部 650ms 清除 visualCue；1～6 格只存活约 650～1075ms。
- 3D Mascot 使用骰子等待 1.02s、每格 0.24s、结束余量 0.18s；1～6 格约需 1.44～2.64s。
- 即使没有其他因素，旧计时器也会在 3D 完成之前清除路径。随后角色进入非路径插值，看起来可能像滑动或被拉到终点。
- activeMotion 在 render 中重建，onActorStep 是内联函数；Mascot 的 effect 依赖整个 motion 对象与回调，普通重渲染可以重置起跑时间。这是已识别的重启机制，具体画面频率需后续定向采样。
- 主界面根据已经结算的 game.phase 提前显示买地等按钮，而 dispatch 另用旧 cue.step 判定是否接受；出现“看得到、按下才说请等候”的矛盾。

### 2.4 界面混乱是结构问题

- 头部仍显示 P3、联网、开发缓存状态等工程信息；重新开局常驻，音效设置塞入回合面板。
- 右侧 turn-card 同时承担身份、账目、新手帮助、当前操作、金融工作台、提示和结果；随着内容出现而不断长高。
- 底部四个 details 分别固定 left，互不排他，没有统一容器。某一项展开后宽度扩大，后面的入口仍留在原坐标，易重叠。
- 页面叠加多份旧 CSS，最后再用 board-3d.css 强覆盖。旧浅色组件、文字、原生控件与深色容器缺少统一契约。
- 主程序实际复用 WorldCanvas，但 rent/outcome 固定传 null，demo 已有的租金和胜负世界演出没有完成接入。
- 头像、棋子色与名称表达没有完全统一；部分正文只 10～11px；地块列表 1 起算，详情与位置 0 起算。
- 标题阶段只是把同一个 turn-card 移到左侧，并用 CSS 隐藏其余字段，底层仍存在棋盘工具和对局 HUD。这解释了为何像网页设置表单。

## 3. 方案取舍

| 路线 | 好处 | 问题 | 结论 |
| --- | --- | --- | --- |
| 继续在现有 CSS 上修颜色与位置 | 初始改动小 | 状态、菜单和演出仍冲突；每增加功能都重新挤压 | 不推荐作为主方案 |
| 保留规则与世界，重建页面层级、HUD 和演出协调 | 保住真实玩法；直接解决混乱与不可靠操作 | 需要收口旧 CSS、明确输入屏障 | 推荐 |
| 整个游戏换技术栈重写 | 结构可以重新设计 | 易损失现有规则、AI、离线与存档；与本次问题不成比例 | 本轮不采用 |

推荐路线分小片交付；不先新建一堆空组件目录。既有 docs/art-renewal/03-frontend-architecture.md 已提出规则状态/展示状态/帧内姿态、命令回执和演出屏障，本方案将其收敛为当前入口的具体交付要求。

## 4. 页面与信息架构

应用顶层区分：启动/加载、标题、新局准备、对局、暂停、结算。系统错误有自己的中文提示和恢复入口。标题与新局阶段不挂载对局 HUD，不靠 CSS 隐藏一整个运行中的对局界面。

### 4.1 标题页

- 全屏小镇美术场景构成一幅完整构图；明确游戏标题、少量角色和一组主菜单。
- 有有效继续记录时显示主按钮“继续游戏”，并在其下显示地图/轮次/玩家摘要；没有记录时主按钮为“开始游戏”。
- 次入口为“新游戏”（有继续记录时）、“读取存档”；“设置”“玩法说明”为低强调入口。
- 不显示回合、资产、地块编号、选地列表、金融、重新开局和开发状态。
- 场景只做低幅待机；减少动态效果时静止。加载期间可先显示可用菜单，避免长时间空屏。
- 显示产品名称，开发仓库名与阶段号放设置的版本信息。

### 4.2 新局准备

- 采用一张独立的准备界面：中部地图预览卡，底部/旁侧 2～4 个玩家席位，固定底部“返回 / 开始对局”。
- 地图卡有名称、预览、格数与当前已有规则摘要；地图选择只改变局部预览，不触发镜头突变。
- 席位直接显示角色标识、名称和“真人 / 电脑 / 空位”。电脑席位可选现有策略；真人姓名直接编辑。人物外观选择只有在已有资产完整支持时才提供，不新增空壳角色功能。
- 常用项目直接可见：地图、席位、规则摘要。默认一名真人加一名电脑，可直接开始。
- “对局设置”二级页放轮数、特殊设施、AI 速度；种子收进“更多设置/复现对局”。快速局可作为现有轮数的预设，必须标明数值，不能虚构预计局长。
- 说明“本机轮流”，避免“多人”让人误会在线联机。允许纯电脑局时明确这是观战配置，不悄悄禁止现有能力。
- 错误就近显示在对应席位/字段，输入保留；开始失败不清空配置。

### 4.3 对局常驻 HUD

| 区域 | 常驻内容 | 进入细节的方式 |
| --- | --- | --- |
| 左上玩家条 | 2～4 个紧凑玩家卡：头像/名称、现金、当前状态；当前玩家明确标记 | 点击玩家打开资产详情；净资产比较在此查看 |
| 顶部中间 | 第 x / y 轮；必要时简短的“电脑行动中” | 不重复铺陈日志 |
| 右上 | 全景/跟随、暂停菜单 | 菜单内含音效、显示、存读档、帮助、返回标题 |
| 底部行动条 | 当前行动者、一句状态、一个主要操作；当前阶段必要的次操作 | 详情随阶段出现，不把所有功能都塞进条里 |
| 当前玩家的工具区 | 手牌入口、资产、金融入口 | 紧凑图标加文字，不单列零库存的五种卡牌 |
| 世界内 | 当前角色光圈、选中地块、短金额或产权反馈 | 位置/归属靠空间与标记解释 |

桌面起始预算：安全边距 20～24px；左侧玩家卡 208～236px；底部行动区约 640～800px、普通状态 80～104px 高；复杂决策卡上限约 180px，超出内容进入独立面板。此为初始设计预算，实际按 1280×720 起验证，不以固定像素强塞所有屏幕。

标准游戏状态不出现常驻右侧大工作台。需要交易时打开完整独立面板；面板打开时给棋盘保留合理可见区，必要时进入菜单模态状态，不把棋盘无限缩小。

### 4.4 元素去留清单

- 全员资产总览、底部玩家菜单、右侧当前玩家重复账目：合并为玩家卡与单一资产详情。
- “当前行动”、角色名、当前位置、phase、最近骰点和多处状态句：保留当前行动者与一条因果明确的消息；历史骰点不长期挂在另一处。
- 开发联网状态、引擎步数/耗时、P3：进入开发诊断/版本页。正常离线不报警；自动保存失败、空间不足等有玩家后果时明确通知。
- 新手帮助与“本步可以做什么”：合并为上下文帮助，可跳过、可重开；仅在真正相关的阶段出现，避免连续弹出说明。
- 四个独立 details：取消，进入统一菜单或统一详情面板系统。
- “按列表选择地块”：改为棋盘导航的次入口，保留键盘和读屏能力，不让屏幕角落长期有莫名加号框。
- “关闭动效”、音效、音量：进入设置；对局中保留必要的暂停、快进/跳过入口。
- “重新开局”：移入暂停菜单，明确保存状态并确认是否离开当前局，避免误触。

## 5. 按回合阶段组织操作

| 展示阶段 | 主要可见内容/操作 | 禁止行为 |
| --- | --- | --- |
| 等待掷骰 | 掷骰；有手牌时显示手牌入口 | 多次提交同一骰子命令 |
| 掷骰与行走 | 骰点、行进反馈；可暂停/跳过演出 | 出现可用的买地/结束回合/交易提交 |
| 无主地产 | 地名、地价、当前租金、购买后现金；购买/暂不购买 | 查看的别块地替换本次购买目标 |
| 自有可建设地产 | 买地/建房/升级的明确阶段；花费和租金变化；建造/暂不建设 | 买地当次紧接着建房；绕过一次到访限制 |
| 他人地产 | 地块与房东高亮、支付者→收款者、实际租金 | 要求玩家额外点击“付租”或重复结算 |
| 公共格/事件 | 简短事件结果，必要时进入对应选择 | 为每条普通日志弹模态框 |
| 商店 | 有限张商品卡、价格、库存、手牌容量；购买/离开 | 非法购买按钮仍可提交 |
| 停留医院/监狱 | 剩余停留回合、跳过本回合 | 显示掷骰按钮 |
| 到访处理完成 | 结束回合；合法的金融操作 | 弹窗后残留点击穿透结束回合 |
| 电脑行动 | 正在做什么、暂停/快进 | 前一演出未完成就执行下一命令 |
| 多真人交接 | 下一玩家身份、我已就位 | 上一玩家继续操作下一人的资产 |
| 已结束 | 获胜者、原因、排名、再来一局/返回标题 | 世界按钮继续改变已结束局面 |

地产决策示例（使用已实测默认地块）：

> 地产 1 · 尚无地主\
> 地价 110　租金 22\
> 现金 1,500 → 1,390\
> [暂不购买] [购买 · 110]

到访自有地时在相同位置换成“建造住宅”或“升级房屋”，直接呈现费用与租金前后值；无需到金融→地产的长列表寻找建设按钮。资产页仍可查看全部地产和合法出售/抵押，但无关地产不堆满“不可建设”按钮。

每个阶段一个主要推进操作；次操作同组且含义明确。按钮稳定，不因反馈文本变化跳位。不要让一次双击的第二下落到已经替换成“购买”的同坐标按钮上；输入按下/释放的归属必须是同一动作上下文。

## 6. 交易、手牌与地图详情

### 6.1 统一面板规则

同一时间只有一个主要面板：资产、银行、股票、存档、帮助等互斥。小型金额说明用局部提示；改变资产的确认用单一游戏内确认层。屏蔽面板背后游戏输入与 Canvas 拾取，焦点进入面板、关闭后回到原入口。

Esc 先关闭最上层可取消面板，再进入暂停菜单；不能把 Esc 偷偷解释成拒绝买地或结束回合。必要决策不靠点击遮罩默认选择。点击地图只查看，不自动购买，不改实际停留目标，不打断当前演出。

### 6.2 银行与借贷

- 独立窗口显示现金、存款，存入/取出是清楚的二选操作，支持常用金额、全部和精确输入。
- 提交前显示从哪个账户到哪个账户、余额前后变化。规则只允许结算阶段办理，则其他阶段为查看模式并说明开放时机。
- 借贷作为银行内独立页签，显示贷款、额度、利率、抵押地产及后果。不与普通存取共用一段含糊提示和同一个银行金额字段。
- 抵押/出售明确选中具体地产并确认，禁止浏览列表时误触即变更。

### 6.3 股市

- 左侧公司/当前价/涨跌，右侧选中公司的买卖操作与本人的持仓。较窄屏幕转为列表→详情，而非横向表格压成微字。
- 数量步进、最大可买/可卖、精确输入并存；显示成交额、手续费、存款余额前后值。
- 股票使用存款，应写“存款不足”，不再泛称“现金不足”。资金变化正负号与账户名一起显示。
- 有真实已收集行情才画历史走势；旧档缺历史则显示当前报价，不生成装饰性假 K 线。
- 买/卖已在交易卡明确展示后，一般小额不再额外弹系统确认；借款、抵押、出售、大额等按现有风险边界提供一次游戏内确认。调整既有确认阈值需独立说明，不能偷改规则。

### 6.4 手牌

- 有卡时显示卡面和数量，不再列“奖励0、步数0、遥控0……”的账单句。
- 遥控骰子直接选 1～6 点；路障进入地图选点，合法格高亮，有明确取消/确认；不使用全地图下拉菜单作为主要方式。
- 使用后显示效果本次是否已启用；一旦实际掷骰按现有规则消耗，表现不能多执行一次。
- 拘留/破产/非本人阶段有清楚限制。键盘可用语义列表选择同一目标。

### 6.5 资产、日志与存档

- 玩家卡进详情，显示现金、存款、贷款、地产、持仓、净资产口径；不在全场显示四份完整财务报表。
- 正常行动只给一条短反馈；日志记录完整因果，面板内可滚动，关键错误持续到被处理。自动保存正常完成不反复刷屏。
- 暂停菜单存档页使用档位卡和存档摘要；手动导入有预览、覆盖确认、保留取消路径；格式/容量错误不改当前游戏。
- 原始 phase、种子等放复现/诊断明细，玩家面对的阶段用中文。人名、资产数、轮数均来自实际存档，不硬编码成两人/60轮。

## 7. 动画与镜头的正确协调

### 7.1 一个事件结果，一次演出

UI/AI → 会话命令入口 → applyAction → 本次 before/after/events → 演出计划 → 骰子→移动→到访揭示→决策/HUD。

- 骰子只由本次 die_rolled 事件触发，关联 actorId 与独立 rollId；买地、存款、选择地块、开关菜单、读档均不触发。
- 使用本次命令返回的事件，而非每次 render 扫描历史事件来推断应重播什么。
- GameState 即时提交并可保存；展示快照直到对应揭示点才切到结果，不能在角色尚未抵达时先把房子、钱和购买按钮一并显示。
- 一个播放器拥有时间。删除主程序旧 cue 的路径计时职责，由真正的完成/跳过屏障解锁下一步。片段、回调使用稳定标识；选地等普通 UI 更新不能重置动作起点。
- 跳过只把展示推进到权威终态，不再次 dispatch；快速、普通、减少动态、跳过四种路径最终规则状态及 randomState 必须一致。
- 新局/读档递增 session epoch，取消旧演出与 AI；旧回调必须无效。后台期间结束当前已提交展示并暂停后续 AI，回前台不补播旧骰子。
- 设置合理异常保护，动画超时自动对齐已提交终态并显示可恢复提示，不能永远锁住回合。

### 7.2 镜头策略

- 明确全景/跟随两种模式，玩家选择持久保存为本机偏好；不随 activeMotion 真假改变模式。
- 默认可采用稳定的中景跟随：玩家进入安全框外才平移，轻微人物待机不会牵动相机。全景能看全地图与所有棋子。
- 位置、lookAt 和 zoom 使用同一连续过渡；切换起点是当前相机实际姿态，允许途中反向切换，无跳帧重置。
- 建议初始标定：模式切换约 400～650ms，玩家交接约 450～700ms；仅为调参起点，不伪称行业统一标准。
- 买地时保持角色/地块镜头，不再次放大或退回全景；金融操作不强制运镜；读档直接定位到当前局面，不从地图中心“飞来”。
- 相机读取 HUD 安全区与实际显示的角色位置，焦点不能被底部决策、左侧玩家条或面板盖住；四角、两图、四人同格都要检查。
- 用户手动浏览地图后暂停自动跟随，提供“返回当前玩家”；不得立刻抢回控制。
- 减少动态模式下关闭自动平移、缩放和弹跳，保留位置、骰点、金额、胜负的静态清楚反馈。

### 7.3 演出节奏与视觉边界

租金用付款者→房东和一个清楚金额；买地只出现产权标记/地基，后续到访才建房；升级有明显外观差异；破产、清算、胜利按事件先后展示，不能还在付租就被结算窗口盖掉。

复用 demo 的租金、结局和金融界面中已验证部分，正式接入前验证 2～4 人、AI、两张地图与旧存档，不能把两人 demo 的假设带入主程序。

遵循仓库全场景统一光照/投影/受影、当前 Three 支持的阴影模式、统一地表高度与薄地砖要求。界面重设计不通过关闭个别物体阴影或加厚悬浮地砖掩盖问题。

## 8. 视觉规范

方向：微缩小镇、温暖奶油色信息面、深墨绿文字与行动底条、克制金色主操作。承接 demo 的亲和感；避免全屏铺满半透明深绿方块。

- 只有主操作使用金色实底；次操作为清楚边界或浅色底，危险操作使用独立语义。玩家颜色只用于身份，不给每个数字都染色。
- 正文优先 14～16 CSS px、重要金额 18～24px、次要说明通常不低于12px；按设备与文字缩放验证，不能通过把字缩到9px来塞内容。
- 文字与实际背景普通重要内容至少4.5:1，大号内容至少3:1；阴影、浅色棋盘移动、不同建筑背景下都要测。不可用整体 opacity 让名称和金额一起褪色。
- 保持 8px 间距体系，面板内16～24px，常用控件触摸目标约44px以上。焦点、悬停、按下、禁用各有明确状态。
- 暂时不可操作但有用的功能保留并解释原因；当前完全不相关的功能隐藏。禁用不是“没有意义内容”的默认收纳方式。
- 统一原创图标，不混用棋子字符、emoji和不相关图形。HUD头像与3D座位形象/颜色一致；未完成形象使用诚实一致的标识，不冒充另一个角色。
- 面向玩家统一1起算编号，内部tileId保持不变；地块具名可作为内容润色，但不偷偷改旧档地图经济和ID。
- 取消说明性废话，如“想做交易？按需展开”；替换为明确入口“银行”“股票”。“现金/存款/净资产”不再统称“资金”。

参考：Xbox Accessibility Guidelines 的 UI context、Contrast、Visual distractions and motion settings 支持清晰上下文、稳定可读、动态效果可控；本方案的颜色、尺寸、布局和时长是针对本游戏的设计建议，不是照搬商业游戏皮肤。

## 9. 响应式和输入

- ≥1280宽桌面：紧凑左上玩家条、底部行动区；鼠标与键盘并用，正文/交易不挤入侧栏。
- 中等/平板：玩家条转顶部横排或紧凑列；长内容用单个面板；不让玩家卡遮住当前角色。
- 手机竖屏：顶部玩家摘要，底部固定主操作；到访/资产/交易使用底部弹层，可展开为全屏。背景必要时仅保留上下文，不强行让复杂股市与棋盘同时可用。
- 手机横屏/短屏：操作卡转短侧面板或两行布局；主操作与关闭按钮始终可见；虚拟键盘打开时金额输入和确认键可达。
- 验收视口至少1280×720、1440×900、1920×1080、2560×1440、390×844、360×640、844×390。并检查200%文字缩放/浏览器放大，不承诺所有设备都用同一空间比例。
- 原生语义按钮与输入保留，可完全游戏化外观；不得为了“像游戏”重造不可键盘操作的假表单。触屏无hover依赖，拖动不触发点选，点UI不穿透Canvas。

## 10. 工程拆分与兼容策略

逐步抽出 ScreenRouter、TitleScreen、NewGameScreen、GameHud、TurnActionBar、PlayerRoster、ArrivalDecision、OverlayHost；按真实需求增加 Bank/Stock/Asset/SavePanel。Session层负责命令、去重、epoch与AI调度；Presentation层负责回执、计划、播放和展示投影；World负责场景与CameraController。

规则层仍是唯一业务权威。AllowedActions/ActionContext统一派生“可见、可用、禁用原因、目标与报价”；UI显示和提交使用同一依据，提交时再核验当前revision/actor/phase。

清理CSS必须先划分新壳层/旧兼容范围，逐屏移除历史规则，避免继续叠!important。旧CSS相关测试逐项确认在保护什么：业务与交互保障保留；只检查特定旧类名/布局的检查改为等价的行为验收，不能删测试掩盖回归。

UI/镜头偏好独立存储，不要求游戏存档升级。旧档按原有规则旗标显示合法操作；不因新局默认propertyVisitOnly=true，就强制改变旧档规则。读档从静态终态恢复，不补播历史动作。不要在本次设计中顺带升级依赖或大改经济。

## 12. 验收矩阵

### 12.1 规则与事件

1. 同种子买地前后position/randomState不变，仅增加购买事件与正常revision；升级、存取、抵押、股票同类检查。
2. 每个die_rolled只展示一次且归属正确；新回合、菜单、读取、重渲染不让旧骰子复活。
3. 一次到访只执行一次地产操作；看别块地不影响目标；现金不足/抵押/满级原因准确；旧档保留原规则。
4. 普通、快速、关闭动态、中途跳过、后台恢复执行相同命令序列，最终序列化GameState完全一致。

### 12.2 浏览器交互

1. 投骰1～6点均经历中间位置后到达，路径未提前清除；选地或开帮助不会重启移动。
2. 快速双击、按住、触屏重复触发，最多提交一次；旧按钮的释放事件不能触发下个阶段CTA。
3. 动画未完时不出现可提交下一动作的按钮；拒绝命令有就近解释而非静默无效。
4. 面板最多一个；打开资产再开银行有确定切换行为；点击遮罩、Esc、返回、焦点恢复符合约定；面板背后世界无误操作。
5. 真人→电脑→真人以及连续真人交接；AI等待展示完成；暂停/快进不改变策略结果或卡死。
6. 菜单/金融操作前后，相机不跳；全景/跟随途中切换连续；关键棋子在HUD安全区；减少动态无非必要运镜。

### 12.3 可玩、存档与发行

保留并运行 npm test、npm run demo:build，按改动补充表现层与真实浏览器检查。现有151项是文档记录的历史基线，本轮未重跑全套，不能写成本轮通过。

至少两张地图各跑真实完整对局；覆盖人机与多人、正常胜负和破产、构建后的PWA离线启动/续局、旧档导入/导出/自动保存；对长期AI/规则保持原固定种子模拟门槛。

检查3D真正渲染，不能只看AX树里的fallback文本或DOM金额变化推断动画成功；必要时采样中间帧与连续截图。手机真机GPU、发热与触摸另记证据，桌面缩窗口不能冒充真机。

### 12.4 视觉与可用性

- 指定视口下主操作不需滚动、无重叠裁切、文字可读；长人名、大金额、四人局、全部手牌、错误提示等极端状态也要检查。
- 建议用3～5位首次试玩者做小规模形成性检查：能否识别标题页、找到开局、知道谁在行动、完成第一次买地、找到存档。人数只是建议，不作为已完成事实。
- 建议目标：无需口头提示便能开始并完成前两轮；没有“刚刚到底执行了吗”的疑问；能解释现金与存款区别。
- 量化遮挡检查针对角色和决策地块的投影安全区；不以一个漂亮截图或某个“屏幕空白比例”单独宣告商业完成度。

## 13. 风险与完成判据

主要风险是时间轴迁移改变AI节奏、旧档规则被新UI误读、多屏面板截断、CSS清理影响旧测试、3D世界事件接入带入两人demo假设。每项以独立切片和跨层测试收口。

完成应意味着：进入就是明确的游戏标题；设置有游戏准备感；对局以棋盘与当前决策为中心；每个菜单有归属；买地不假重掷；镜头不抢夺控制；完整玩法、旧存档和离线运行继续成立。不能以“改成全屏”“更换配色”“所有单元测试通过”单独替代上述验收。
