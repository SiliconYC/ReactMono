# Yakamozli/richman-3d 深度研究：程序化三维棋盘的实际边界

> **任务**：[ReactMono Issue #102](https://github.com/SiliconYC/ReactMono/issues/102) · 研究对象：[Yakamozli/richman-3d](https://github.com/Yakamozli/richman-3d) · 独立分析，不导入上游源码及素材。  
> **核心结论**：这是以 **Monopoly 式 52 格外环平面棋盘为底、角色/房屋/骰子为 3D 几何**的原创网页作品，不是 1998 年《大富翁4》严格复刻；“程序化绘图”不等于“全场景三维建模”。对 ReactMono 最有价值的是代码生成的 **卡牌/地契/纸币美术管线**与少量交互点子，而非替换现有真正 3D 地块街区。[B01][B02][B03][B07][B17]

## 二、产品目标及与原作关系

它的 [README](https://github.com/Yakamozli/richman-3d/blob/32e7f01f9888a28b8fd1267f5488c455e15abe4a/README.md) 使用“完全复刻经典大富翁核心玩法”的宣传措辞 [C01]，但其游戏系统实为**受 Monopoly 与《大富翁》系列共同启发的改编作品**（`original_relation=inspired`）：

- 设计采用 **52 格、14×14 的正方形环形行走路径，16 组×2 城市**；`js/config.js` 定义双骰、经过起点 `¥3000`、监狱、车站、公用事业、色组垄断后建房及酒店。[B01][B09]
- 上游自己的 [`docs/research.md:17-40`](https://github.com/Yakamozli/richman-3d/blob/32e7f01f9888a28b8fd1267f5488c455e15abe4a/docs/research.md#L17-L40) 直接描述 Monopoly 价格、两骰、成组建房、车站和公用事业倍率。不能将这些机制等同于《大富翁4》完整规则。[B13]
- 开局角色姓名与服饰**明显参考了原作角色人物特征**，上游研究表写出“小美/阿土/夫人/贝贝”等与角色的对应关系；“由代码绘制”不必然意味着人物形象独立或已经获得商业授权。[B15]

故分类既不是逆向工具，也非原版兼容移植；它**不能**作为《大富翁4》精确经济、股票、银行、地图事件和神明玩法的规则依据。它的核心用途是程序化图像美术与极轻量 3D 组合建模参考。[B01][B07][B09][B13]

## 三、代码架构与数据流

上游无需 Node 打包即可从 `index.html` 经 importmap 加载本地 `vendor/three.module.js`；`js/main.js` 将 `scene`、`game`、`ui`、`ai`、`sound` 注入组织。项目单元大致如下。[B16]

| 模块 | 已核对责任 | 实际耦合与边界 |
| --- | --- | --- |
| `js/config.js`（172 行左右） | `TILES`、`GROUPS`、牌/角色参数，`tileGrid/tileWorld` | 地图布局以固定数值、下标与固定中心坐标驱动，不是可装载地图数据 |
| `js/draw.js`（约 1,034 行） | Canvas 2D 绘制棋盘、骰面、纸币、地契、牌、角色头像、地标剪影 | 巨型绘图模块，图形风格、内容字符串及配色混合 |
| `js/scene.js`（约 852 行） | Three.js renderer、贴图棋盘、角色网格、房屋、相机、射线拾取、动画 | 自己维护动画数组与每帧渲染；场景和视觉对象集中在一个可变单例 |
| `js/game.js`（约 726 行） | 单例状态、异步任务链、骰点、移动、落地处理、金钱及胜负 | 通过 hooks 调用 scene/UI；离开浏览器的无头桩可覆盖部分路径 |
| `js/ai.js`（约 72 行） | 资金阈值购买、盖房、使用道具的简易策略 | 使用 `Math.random`，非可复现策略测评系统 |
| `js/ui.js`（约 862 行） | DOM 开局、HUD、地契面板、五选一翻牌、资产等 | DOM+图片覆盖 WebGL 场景，未见 React 组件 |
| `js/sound.js` | WebAudio 合成音效与循环音乐 | 以浏览器用户交互解锁，与独立渲染性能未测 |
| `test/smoke.mjs` | 无头调用 `game`、桩掉 scene/UI、检查状态不变量和清算 | **脚本存在≠在本次通过**；不测真实画面/设备/长时稳定性 |

主要调用链：`main.js → game.startGame → game.run(异步队列) → game.doRoll → game.moveForward → scene.movePlayer → game.land → (买地/收租/牌事件/监狱) → ui.updateHUD → game.endTurnCheck / endGame`。[B09] 各模块不是完全纯函数架构：`game` 自有可变 `state`；`scene` 存 mesh Map、动画队列与 DOM 监听。测试使用 stub hooks 验证逻辑可脱离 WebGL，但不等于完备的规则隔离或确定性复现。[B09][B11]

**存档**：已查入口、`game.js` 及 UI 主路径未取得可证实的保存/加载 API，故矩阵记 **未知**，而不写“绝对不存在”。未见服务器端、账户与多地图配置的明确源证；仓库结构本身是静态页，是否适合 PWA 断网缓存仍需另行审计。[B01][B09][B16]

### 对照现代商业级 Q 萌低多边形方向

**源代码足以支持的相对判断**：ReactMono 的场景是可随地图数据变化的**实体地表、道路、建筑与角色**；上游的棋盘主体在三维空间中仍是一整张平面画布，3D 局限于摆件、房屋、骰子、角色。因此针对**“现代沙盘城市的结构可扩展性”**，ReactMono 明确**优于**上游 [B01–B05][B17]。反过来，针对**“用零美术文件快速批量产生地契/卡牌/纸币并保持一致描边”**，上游实现覆盖更全面，值得专门学习 [B07][B08]。这两项为源码级比较，不是贴图品质或审美实测。

**不能支持的判断**：上游 README 的“苹果美学”“全部代码绘制”及作者 3 张截图，不能证明真实游玩时画面达到《天天过马路》级商业 Q 萌标准；也不能仅因 ReactMono 使用实体几何，就宣称它已经获得商业级 UI、相机或整体体验。**本研究不编造二者的观感胜负**，画面实景评分记 `null`。[C01][C02][D01]

## 五、五处技术深挖与预算测算

### 5.1 原始参数映射与整张棋盘生成 [B01][B02]

`GRID=14`、`CELL=210`，`tileGrid(i)` 把连续编号映射到环形外圈；`boardCanvas()` 先绘公园、十字大道和中心徽章，再对每个 `TILES` 调用 `drawTile`，并输出整个 Canvas。随后 `scene._buildBoard` 把唯一大贴图附在 **`BoxGeometry(14,0.55,14)` 的 +Y 顶面**。所谓“程序化三维棋盘”准确讲是**Canvas 绘制棋盘 + WebGL 环境照明**；不能当作动态凸起路缘、3D 城市街道或自定义不规则路线。[B01–B03]

静态资源预算（理论值，**不是 GPU 性能测量**）：

- 单张棋盘 Canvas 分辨率 = `14 × 210 = 2940`，面积 **8,643,600 像素**，按 4 字节像素至少约 **34.6 MB（约 33.0 MiB）** 的未压缩像素数据；生成 mipmap 时同格式纹理约 **44.0 MiB**，实际还可能保留 Canvas CPU 备份、其他纹理与显存对齐开销。
- 阴影图设置 `2048×2048`，硬件成本与格式相关；不要未经 profiling 直接称“可在手机 60 FPS”。
- `setPixelRatio(min(devicePixelRatio,2))` 最高给出双倍设备比例；`scene._loop` 无论是否存在交互持续申请动画帧，与 ReactMono 在闲置状态可采用需求渲染的策略存在能耗差异。[B06]

建议在目标硬件用浏览器性能面板分别测 **静态棋盘占用、渲染帧时间、draw calls、纹理大小与内存增长**，不要拿静态贴图文件大小代替显存数字。[B02][B06]

### 5.2 程序几何角色与房屋 [B04][B05]

`_buildCharacter` 按 `CHARS[].style` 装配头身、发型、配件、耳朵/尾巴和脸部；几何是多 Mesh Group，不涉及贴图贴骨与动画骨架。`updateHouses` 为房/酒店分别造 Box/Cone 子模型，按产权色上色，购买/升级以弹跳缩放出现。这一思路适合低成本原创 **小地标、道具、店铺模型原型**；但如果无实例化和资源复用，放大到数百格会制造多物体开销，且复杂角色表情、姿势复用比骨骼/网格资产难管理。不要把“自动绘制一个卡通物体”称为“现代商业级低模角色已完成”。[B04][B05]

### 5.3 画布产生卡牌、地契、纸币、UI 贴图 [B07][B08]

`diceFaceCanvas` 输出 256² 点数画布；`cardFaceCanvas` 输出 **400×560** 的边框、顶部色带、图标、自动换行正文；`drawLandmark` 等绘城市特色剪影；`coinCanvas` 为 Sprite 提供 64² 圆片纹理；`buildingCanvas` 制作简化窗面。这比反复寻找授权一致的 32 城地契素材可靠，但本质上仍是**绘制 2D 卡面**：可显示在弹层的 `img`，也可做 Three.js 贴图，却不能直接变成 3D 建筑。[B07][B08]

ReactMono 可用项目自有矢量/Canvas 绘制器在构建时或缓存时生成卡面，统一文字、产权色、名义金额、稀有度与留白；保留原有 React 信息结构和 Three.js 沙盘，不搬运上游卡图及角色名称。需做字体回退、窄屏可读性、中文换行与缓存回收的浏览器测试。

### 5.4 光照、镜头、输入与动效 [B06]

`HemisphereLight` + `DirectionalLight` + `PCFSoftShadowMap`；自由视角 `OrbitControls`，跟随时平滑更新 `controls.target`，接管手势时暂停；Raycaster 对单个棋盘 Mesh 求交后转格子索引。这些机制**适配其固定正方形贴图**，不能直接迁移至 ReactMono 已经变化的地图拓扑、遮挡和阴影相机配置。可参考“自由/跟随模式切换 + 用户拖动时暂停自动追踪”的交互规则，在 ReactMono 的 `CameraRig` 增量验证，不应导入 `scene.js`。[B01][B06][B17]

资源风险：持续渲染循环、动态图集材质、重复重建 `updateHouses` 子 Mesh；`_houseContainers` 清空子节点只移出场景，片段未见相应逐几何/材质 `dispose`，可能形成**潜在**内存增长，而不是已经证实的泄漏。要靠反复买卖与堆内存测量确定。[B05][B06][D01]

### 5.5 实际规则逻辑、AI 和测试盲区 [B09–B13]

`game.land` 对地产/车站/公用事业分支执行买/租，事件由 `drawCard` 处理；`test/smoke.mjs` 测回合胜利、产权、房数、破产与自定义资金，属于**存在有价值的测试定义**，本次未执行。AI 的买入条件是资金阈值/财产组成本比较，遥控骰与其他行为有 `Math.random`，无确定随机种子证据。[B09–B11]

发现两个可复核的质量问题：

1. **截图测试路径错误**：`test/shot.html:8` 对 `three` 的 importmap 为 `./vendor/three.module.js`，从 `/test/shot.html` 实际会解析为 `/test/vendor/three.module.js`，但树中只有根目录 `vendor/three.module.js`。`index.html` 的同样写法因在仓库根目录才正确。此外 `test/shot.js:40` 把 `document.body.textContent` 改成状态文字，可能直接清空截图页 Canvas。因此**不能依赖截图页声称完成独立视觉验收**。[B12]
2. **作者文档与运行配置不一致**：`docs/research.md` 仍描述 **40 格、起点 ¥2000**，而 `js/config.js` 已定义 **52 格、起点 ¥3000**。研究报告以运行代码的常量为准，原机制来源笔记只保留为设计历史，不能作为原版忠实度的证据。[B01][B13]

## 七、缺口、矛盾与许可证风险

1. **可运行性与截图**：没有本次独立 A 级游戏执行；网页无法读取，真机未测。仓库中的三张 PNG 属作者素材且本研究未查看/二次传播实际画面，不标注为我们的实测。[C02][D01]
2. **截图/测试设施**：`test/shot.html` 的 importmap 与实际文件树不匹配；`smoke.mjs` 只覆盖关键规则不变量，不是所有规则边界，更不能替代画面/多人操作体验。[B11][B12]
3. **性能与架构**：单幅棋盘贴图较大；持续 RAF、动态 Mesh/材质生命周期及光照阴影参数未经过目标手机 profiling，容量/画质结论均待 A 级测量。[B02][B05][B06][D01]
4. **规则血缘**：固定外环、双骰、色组酒店和车站制属于 Monopoly 式机制；作者研究文档中留有 40/52 格与 ¥2000/¥3000 的历史冲突；不能误用作 1998 年原版规则独立交叉验证。[B01][B13]
5. **MIT 与二创**：根目录 [MIT 许可证](https://github.com/Yakamozli/richman-3d/blob/32e7f01f9888a28b8fd1267f5488c455e15abe4a/LICENSE) 有修改和再发布授权条件，**但不代表原版著作权人授权角色、标志建筑剪影、商标或近似视觉设计**。尤其 `docs/research.md:26–35` 自述经典角色参考关系；仿作侵权风险需要专业核查，ReactMono 应只学习抽象设计，不复制具有识别度的造型。[B14][B15]
6. **第三方文件**：`vendor/` 内含 Three.js 与 OrbitControls 的上游代码；根仓库标 MIT 不取代对该第三方原始版权声明、版本与依赖修订的独立核验。GitHub 元数据显示 `fork=false`，不能据此排除借用或派生来源；本次无相似性扫描。[B14][B16]

## 九、结论与下一步

**判定：`read_only_reference`（只读技术参考）**。不要借上游项目重写 ReactMono 的 React/Three.js 主架构，也不要改核心经济规则。可优先在未来独立 Issue 验证 **原创地契/卡牌自动绘图**、**等级升级动效**、**用户镜头接管** 三项低侵入试验；建议每项先用实际截图与设备记录设明确收口线。该任务的工作仅限研究交付，不擅自建立大量新 Issue。[B03–B08][B17]

尚待证实：公开版在真实浏览器上能否开局、连续多轮买卖/清算；修复 `test/shot.html` 测试路径后的图形表现；不同屏幕下的 HUD 可读性；持续渲染和巨大 Canvas 纹理的性能；存读档/银行/股票等功能是否另有可验证实现；第三方依赖与经典角色是否具有充分权利基础。**未完成这些验证，不宣称“商业级完成”或“忠实复刻”**。[B11–B16][D01]
