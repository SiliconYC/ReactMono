# 外部开源《大富翁 4》项目研究与验收标准

本规范仅管理 `docs/research/` 下的对外研究成果，不替代 `AGENTS.md` 的开发、安全与产品规则。**每个研究者先读仓库主 README、AGENTS、此规范和自己的 Issue**。

## 1. 范围与方法

- 每个 Issue 锁定一个上游 GitHub 仓库，读取 README、LICENSE、文件树、关键实现和测试，不可只摘录项目介绍。
- 必须记录上游 URL、默认分支、**研究时的精确 Commit SHA**、检查时间（UTC）和 LICENSE 路径；仅有年份或“最新版”不合格。
- 依据任务研究原版规则/资源逆向、渲染、架构、测试、打包/可玩性；优先选择至少 3–5 个有代码定位的核心发现，说明对 ReactMono 的真实价值与限制。
- 原版《大富翁4》（1998）与资料片、其他代、其他玩法的同类作品分开处理；不能把“灵感借鉴”写作“忠实复刻”。
- 对上游称“测试通过”“真机运行”“完整复刻”须先标注「作者声称」，独立验证后再升级证据；不可从代码结构直接推断完整可玩或商业级视觉。
- 源码归属、fork/复制、许可证继承与版权素材风险必须单独调查；除非经所有者另行授权，**本任务只做分析，不移植上游源码或素材、不改游戏核心**。
- 外部依赖、原版素材、注册用户与密钥不足时，不隐瞒限制；可以做无需私有资产的静态审计和不含素材的单元测试，准确记录跳过项。

## 2. 证据分级（逐项标明）

| 等级 | 依据 | 可支持的结论 |
| --- | --- | --- |
| A：独立实测 | 研究者在可说明的环境实际编译、运行、截图或测试，并存验证命令/输出及上游 SHA | 特定环境下该功能确实可运行；不自动证明忠实原作或全面完成 |
| B：源码核查 | 对固定 SHA 的代码、配置、测试用例及行为路径进行了可追溯定位 | 某项实现存在，以及代码级工作方式；测试定义不等于测试已运行 |
| C：上游自述 | README、状态报告、Issues、视频、Release 或作者提供的日志 | 作者声明了目标/结果；不能作为独立实测 |
| D：推断或未验证 | 二手转述、搜索摘要、推测及资料不足 | 仅列为假设、待证实，不得作确定性结论 |

每一条关键判断至少关联一个 `evidence_id`；负面结论也必须有证据，不能因为未搜到就直接断定“没有此功能”。对截图必须说明是上游截图还是本项目实测截图，允许缺失但不得伪造。

## 3. 单仓库交付位置

统一路径：`docs/research/repositories/<owner>--<repo>/`（GitHub 上游大小写照录，原有同名目录只增量更新）。

必须存在三个有实质内容的文件：

1. `README.md` — 深度报告，遵循下列九章。
2. `source-index.md` — 至少 3–5 处关键源码证据，含路径、函数/行号范围、上游 SHA、URL、简要原理、可验证命令（适用时）。
3. `evidence.json` — 可解析 UTF-8 JSON，记录事实、证据等级、验证状态、功能覆盖/评分/许可风险；与报告一致。

九章报告：

1. **研究身份与复现基线**：仓库 URL、版本/提交时间、默认分支、最后更新时间、fork/upstream、许可证、研究者执行环境。
2. **产品目标和与原作的关系**：严格复刻/玩法衍生/资料片/工具、与原版 1998 年《大富翁4》的界限。
3. **代码架构与数据流**：入口、核心模块、依赖、规则-渲染分离、地图/存档结构、测试与可运行产物。
4. **功能完成度矩阵**：新局/回合、地图、地产、银行股市、卡道具、神明事件、AI、存读档、UI/动画/音频、端侧；每行注明“证实/部分/未知”和证据。
5. **核心技术与原版证据**：3–5 个真实源码深挖点，必要时逆向函数/原版数据对照，标明是否独立验证。
6. **对 ReactMono 的可借鉴点**：至少 3–5 项，按价值/实现成本/与现有架构的兼容性排序；给出可复现路线但不在研究 Issue 中改代码。
7. **缺口、风险及矛盾**：真实玩家体验、商业级视觉、浏览器/PWA限制、许可证与商业素材、作者说法和代码证据不一致之处。
8. **五维评分（各 0–5）**：原版规则覆盖、代码可维护性、独立可复现性、画面与交互完成度、对 ReactMono 的实用价值。每项列证据和置信等级；证据不足必须填 `null`，禁止捏造总分。
9. **结论与下一步建议**：复用/只读参考/排除；列明确的未解疑问、后续 Issue 候选，区分已验证与建议。

## 4. JSON 最低契约

`evidence.json` 应有以下字段（采用标准 JSON、不得注释）：

- `repository`（上游 `owner/repo`）、`url`、`checked_at_utc`（ISO8601）、`upstream_sha`（完整 SHA）、`original_relation`（`faithful|derived|inspired|tool|unknown`）。
- `license`（`spdx`、`source_url`、`risks` 字段；未核实时允许 `null`）。
- `execution`（`attempted`、`environment`、`commands`、`result`、`limitations`；未执行须填写原因）。
- `evidence` 数组，每项 `id`、`level`（A/B/C/D）、`claim`、`source_url`、`locator`、`verification`、`limitations`。
- `features` 数组：`feature`、`status`（`verified|partial|claimed|unknown|absent`）、`evidence_ids`；`absent` 需有实证。
- `scores` 对象：`rules`、`maintainability`、`reproducibility`、`presentation`、`reactmono_value`，各 0–5 或 `null`，并在正文解释评分依据。
- `recommendation`（`read_only_reference|candidate_for_adaptation|exclude|more_evidence_needed`）和 `open_questions`。
- 所有证据引用 ID 必须能够在本 JSON 的 `evidence` 中解析，JSON 不应含机器私有绝对路径、敏感信息或无法查证的虚构输入。

## 5. 验收、提交和收口

- 研究者从最新 `dev` 创建**一个 Issue 对应一个独立临时分支**，阶段性 Commit/Push；不修改 `main`。
- 如工具与资源可用，至少运行研究产物 JSON 解析与链接/路径核对；代码实测如不能执行写明原因。检查研究文件是否真实、九章齐备、证据匹配、许可证状态明确。
- 不为每次 Push 运行全量游戏 CI；遵守现有工作流和最终合并前必要验收。不得以测试“绿”掩盖视觉/规则缺口。
- 发起 PR 合并 `dev`，在 PR/Issue 列出精确上游 SHA、报告路径、至少三个证据锚点、未验证事项与验收结果；合并后关闭 Issue、补齐索引。
- 不创建空目录/.gitkeep、空报告、“待补”JSON 或凭空生成的截图；本地克隆与研究中间文件不入 Git。
